# DNDTurn：同步交互与环境进度分离——重分类与重构指导

**版本：1.0 · 2026-09-26**  
**状态：设计指导与静态源码审查；不是已实现功能报告。**  
**目标快照：`DNDTurn-sources(20260926-104127).zip`。**

> **核心契约：直接操作与同步响应按原版执行；一旦进入被托管的延时、周期、生产、流体或危险过程，就由环境参与者推进。分类不取决于最初触发它的玩家，也不要求继承某个行动的授权。世界时钟不是环境回合的专属开关。**

本指导替代此前目录中“通用获准后续反应 / REACTION 授权继承”的建议。此前目录中的源码片段仍可参考，但旧的分类结论不得覆盖本文。

## 0. 来源、适用范围与决策等级

当前目标在 `targets/neoforge-26.1/gradle.properties` 中声明 `neoforge_261_version=26.1.2.84`，目标构建使用 Java 25。原版核查参考为用户资料库中的 `minecraft-patched-26.1.2.109-sources.jar`。两者不是同一补丁版本；实施前必须在目标 `.84` 源码中复核方法描述符、调用顺序和 NeoForge 钩子，不能为消除差异而擅自升级依赖。[S01]

本次未修改项目代码，未编译，未运行客户端、服务端或 GameTest。源码证据包含原始文件路径、行号、SHA-256 与必要摘录，见同目录的 [源码证据附件](DNDTurn_Environment_Tick_Refactor_Evidence_20260926.md)。文中 `[Sxx]` 对应附件章节，不是虚构的在线引用标识。

| 等级 | 本文含义 |
|---|---|
| 已明确的玩法要求 | 无延时供电可立即点燃 TNT；中继器延时先等待环境；TNT 的有效引信与爆炸属于环境过程；漏斗自动工作要等环境；不用玩家来源追踪 |
| 本文建议的实施基线 | 按回调通道粗管、精确维护白名单；TNT 的物理与引信作为同一环境实体步处理；普通荷叶船碰破坏按当前接触在环境步骤复查 |
| 仍需目标版本验证 | `.84` 注入点；新实体在同一步的更新资格；跨阶段精确顺序；涉及模组自定义行为的兼容性 |

只控制遭遇/环境所属的精确区域。区域之外保持原版；多遭遇间的归属、合并和卸载使用现有生命周期机制。不能仅凭“这个维度有一个环境回合正在执行”就让所有遭遇的托管过程同时推进。

## 1. 不再按“有影响/无影响”或“是谁触发”二分

### 1.1 三种执行策略，外加显式适配登记

| 策略 | 对象 | 行为 |
|---|---|---|
| `DIRECT`：直接执行 | 获准主动操作的当前调用，以及未被专门托管的同步状态响应 | 保留原版处理，不为每次邻居响应申请行动权；可以立即产生战术结果 |
| `ENVIRONMENT`：环境进度 | 计划方块/流体更新、选定的随机/天气更新、服务端生产与周期逻辑、TNT 等明确危险过程 | 仅消费所属环境规则授予的有效步骤；纯等待不推进、不补算 |
| `PASS_THROUGH`：常规直通 | 未纳入托管的普通更新；已审计的客户端表现、生命周期维护 | 沿原版运行，不占用环境进度 |

“显式适配”不是第四种行动权，而是登记某个不在常规 tick 通道里的入口也执行 `ENVIRONMENT` 策略。例如漏斗接触吸入、按规则延期的荷叶船碰破坏、某些持续接触效果。

**不得创建通用 `AUTHORIZED_REACTION`、`rootActionOwner` 或 `causalLease` 作为方块延迟更新放行前提。** 日志/击杀归因可以保留来源，但不能将“归因数据”变成“环境过程是否允许运行”的资格。

### 1.2 分类的是“具体行为”，不是完整方块

同一个按钮有直接按下与延迟复位；同一 TNT 有直接点燃与环境引信；同一漏斗有合法玩家存取与自动运输。它们不能共用一个整类布尔标签。

建议策略键包含：`逻辑侧 + 回调通道 + 方块/方块实体/实体类型`，必要时增加 `事件 ID / 状态分支`。位置和环境归属用于决定在哪里应用策略，而不是单独决定一切。

`DIRECT` 也不是“任何函数只要不是 tick 就无条件安全”：漏斗接触转移就是反例。应先匹配明确登记的过程覆盖，再落入通道默认值。

### 1.3 同步后果与未来任务的边界

```text
主动操作入口：校验行动权 → 执行原版逻辑
    同步 setBlock / 邻居通知 / 直接供电：继续原版
    scheduleTick / 延迟状态机 / 周期进度：进入各自的环境调度
```

环境步骤内部产生的同步后果也照常执行。若这些后果又安排了新的延迟任务，新任务仍按原始 delay 排队，不继承一次性“全部立即执行”的许可。

原版 `ScheduledTick` 只保存类型、位置、到期时间、优先级、顺序；去重主要按类型和位置，没有通用玩家来源。不要为本阶段另造跨 tick 因果图。[S02]

## 2. 三条基准行为序列

### 2.1 按钮/拉杆 → 无延时供电路径 → TNT

```text
玩家合法操作
  → 开关状态立即改变
  → 原版同步供电与邻居响应
  → TntBlock 的点燃路径生成 PrimedTnt，按原版条件移除 TNT 方块
  → 当前操作结束

玩家思考
  → TNT 不消费有效引信，不因等待自行爆炸

所属环境步骤
  → 推进 TNT 的环境实体步
  → 引信耗尽时沿原版爆炸链执行
```

`TntBlock.neighborChanged()` 在有信号时直接走 `onCaughtFire()`；参考补丁最终创建 `PrimedTnt`，不是先为 TNT 方块安排计划 tick。原版规则、取消/失败分支与音效事件均应保留。[S03][S04]

注意：这里的“直接供电”不包括中途实际经过发射器、侦测器、中继器或已被归环境的活塞事件。是否有等待边界以实际调用路径为准，不以玩家主观称呼“拉杆释放 TNT”为准。

### 2.2 按钮/拉杆 → 中继器 → TNT

```text
玩家合法操作
  → 按钮/拉杆立即改变
  → 中继器登记 scheduled tick
  → 纯等待不消费这个 delay
  → 此时下游 TNT 尚未因该延迟输出而被点燃

环境有效时间到达
  → 中继器执行原版回调并改变输出
  → 下游同步响应可以立即点燃 TNT
  → TNT 随其环境实体时间推进至爆炸
```

中继器不是方块实体 ticker；参考实现使用 `DiodeBlock` 计划调度，延迟由档位给出，并保留优先级/锁定语义。[S05]

**不额外强制“中继器触发后，再等整整下一轮才能开始 TNT”。** 若当前环境窗口尚有步骤，TNT 按原版阶段资格与剩余预算运行；不足时跨环境回合继续。

### 2.3 “在环境回合爆炸”不等于“下一个环境回合必炸”

参考 TNT 默认引信为 80；当前配置代码给出的默认 `environmentTicks` 为 20。未被外部配置覆盖、未被其他机制改写引信时，从满引信开始需要 80 个有效 TNT 环境步，通常占四个完整 20 步窗口。不能看到 TNT 后把引信清零，也不能擅自把默认环境预算改成 80。[S01][S04]

中继器本身的延迟要单独消费；爆炸连锁可改变后续 TNT 引信，必须保留原版结果。精确到第几个物理阶段的差一问题，需按目标版本队列顺序测试，而不是硬编码一个跨轮数。

按钮自动弹起属于计划更新，也等环境有效时间。按钮在玩家思考期间保持按下是本规则的预期结果，不是需要自动补跑的故障。[S03]

## 4. “荷叶”必须分成两种原版方块

### 4.1 大型垂滴叶 `BigDripleafBlock`

其计划回调确实推进倾斜：踩踏先进入 `UNSTABLE`，之后的 `PARTIAL`、`FULL` 与复位依赖计划更新。把这些计划步骤归环境即可覆盖该条倒伏链，不需要玩家来源标签。[S06]

同一类还有投射物命中立即完全倾斜，以及通电立即复位。这两条不是计时步骤。本文按“同步直接、计时环境”的主规则保留直接分支；若明确要求这两条也等待，增加具体入口覆盖，而非悄悄假定它们已经被 scheduled tick 门禁挡住。

### 4.2 普通荷叶 `LilyPadBlock`

参考源码没有倒伏计时。其 `entityInside()` 在服务端检测到 `AbstractBoat` 时直接 `destroyBlock()`；支撑规则来自它自己的 `mayPlaceOn()` 和继承的植被逻辑。[S06]

为落实“荷叶的这种环境后果也要等待”的字面要求，本文将**船碰破坏**登记为环境接触过程，而不伪造一个 LilyPad ticker：

- 非所属环境步骤：抑制这一破坏分支；必要时登记有界的待复查位置，而不是缓存 Entity 活引用。
- 所属环境步骤：检查区块仍加载、方块仍是同一受支持机制、当前确有符合原版接触条件的船；满足时执行原版破坏分支。
- 船已经离开、方块已经改变：清除候选，不对未来新放置荷叶重放旧接触。候选按位置/生命周期去重并在卸载/结束时清理。

**这是新增规则，不是原版已有计时。** 基线采用“环境时刻的当前接触”，不是“无论船后来在哪里都补演历史破坏”。两者的结果不同，必须在测试名称和用户说明中写清楚。不要通过扩大整船冻结来掩盖这个语义选择。

## 5. TNT 的实施基线与物理边界

### 5.1 最低目标与推荐目标

最低目标是“引信只在环境进度中消耗，爆炸只从合法环境更新发生”。但如果仅暂停引信，让 TNT 在等待时仍随重力/水流移动，思考长度可能改变爆炸位置。它也会改变 TNT 大炮中的飞行与引信比例。

因此，**本文推荐把受控 TNT 的整个原版模拟步作为同一环境过程：移动、碰撞、流体接触、引信、到期爆炸保持原有内部顺序。** 这是对 TNT 这一明确危险实体的局部特判，不是恢复对所有实体和物理的统一禁令。[S04]

如果后续玩法明确选择“位置可在等待时自然变化但引信不变”，可以拆分；必须将其标成较弱的时间隔离规则，不能宣称与上述严格等待不变量等价。

### 5.2 不要手写爆炸或手动补 tick

保留 `onCaughtFire()` / `prime()` / `PrimedTnt.tick()` / `explode()` 的原版与 NeoForge 钩子。不要从按钮 handler 直接调用 `level.explode()`；不要每轮把引信减固定秒数后另造伤害；不要重新手写战利品链。[S04]

环境阶段给 TNT 一次原版实体更新机会，须尊重原版全局 freeze、区块/实体有效性和更新容器。禁止在同一个服务器 tick 手动循环调用 TNT 的 tick 来消耗整轮预算，这会脱离流体、红石、碰撞和实体更新的阶段顺序。

当前 `prepareEntitySimulationStep()` 的普通实体路径仍是“区域内无有效 MobMoveLease → 暂停”，没有 TNT 的环境类别。仅恢复方块点燃不会使 TNT 在环境阶段自动运行。新增策略必须同时用于纯查询与执行入口，并高于旧的普通实体默认分支；不得解除所有 Mob 冻结以绕过这个缺口。[S10]

客户端不得用真实等待时间把 TNT 提前倒数消失；表现应服从服务端权威环境状态。需要检查现有客户端暂停/实体表现协议，不能只修服务端。

### 5.3 外部作用与归属

原版爆炸的来源/点燃者归因继续保留，但不用于验证“环境是否有权爆炸”。有效环境主体是所属遭遇，不是某位仍然在线的玩家。[S01][S04]

TNT 离开/进入其他受控范围、爆炸影响相邻遭遇、传送、卸载恢复，都必须进入现有域边界策略或明确的新适配。无法证明边界正确时，报告为该场景未完成；不要永久冻结、丢实体或自动重放一次有副作用的爆炸。

## 6. 漏斗：把整个自动运输过程归环境，而非只拦一个 ticker

参考源码的自动路径至少包括：

```text
pushItemsTick → 冷却变化 → tryMoveItems → 推出/吸入
entityInside → tryMoveItems → 接触物品吸入
```

因此，接触吸入与 ticker 应共享同一“所属环境正在执行”的判断。在 `.84` 检查完整转移调用图，找准共同的自动行为边界，避免上层被拦但旁路仍调用库存变更。[S07]

规则要求：

1. 纯等待时冷却不减少，库存不因自动转移改变，接触物品不被自动吞入。
2. 环境步骤按原版顺序推进冷却和自动转移，不给一次 ticker 再人为添加第二次吸取。
3. 玩家通过合法容器操作存取，不与自动运输共用禁令；接收一个已经合法执行的输出也不应在通用库存 API 被无差别拦截。
4. 目标漏斗/容器属于其他域时，检查跨域规则，不因源漏斗有环境权就自动推进目标域的自主步骤。
5. 若延迟的是“扫描是否有物品”，环境步骤重新扫描当前世界；物品已被合法捡走时不得凭旧引用复制物品。
6. 不对无限经过的物品逐个建立待转移事件。优先托管过程本身，而非记录每次失败的接触调用。

## 7. 现有框架应保留与修改的部分

### 7.1 现有环境参与者已经有可复用的执行归属

`CombatEngine.authorizeEnvironmentStep()` / `commitEnvironmentStep()`、`ServerCombatService.activeEnvironmentSteps` 与 `activeEnvironmentEncounters` 已提供命名步骤和遭遇归属。错误结果记录也用 encounterId 作为稳定环境主体。首轮无需在世界里生成假实体，也无需新建第二套回合引擎。[S01]

现有 `RegionalScheduledTicks` 对区域内计划更新进行托管，并保留 `remaining`、优先级、顺序、`bornStep`、去重及保存衔接。**在本轮新分类下，它不是应该被删除的错误设计，反而是计划更新归环境的主要基础。** 需要收缩的是“同一位置暂停判定统治所有更新”的含义，以及补齐特例，而非全面释放计划队列。[S10]

### 7.2 文件级修改职责

以下类型名称中，现有文件为源码真实存在；新增抽象名仅为建议，不要求机械拆成同名文件。

### 7.3 决策顺序的概念草图

以下只是职责示意，不是可直接粘贴编译的实现：

```text
原版前置条件不允许运行 → 尊重原版
不属于受控域           → 沿原版
存在精确过程覆盖       → 应用该覆盖（如 Hopper 接触也归 E）
命中精确维护/显示豁免   → P
当前是直接同步响应     → D
属于受管控时间通道     → E
其他未纳入过程         → 沿原版，并按审计范围说明限制

E 的执行资格：当前位置/实例所属环境有合法且未重复执行的有效步骤
不是：原始发起者仍持有回合、附近最近有人点过方块、ThreadLocal 残留了行动 ID
```

直接交互的主体鉴权仍在上层主动行为入口。上面的策略不能替代攻击、放置、破坏、容器操作的资源和权限校验。

## 8. 有效环境时间：保留原版相对时序，不让思考时长混入

### 8.1 计划更新

世界 `gameTime` 默认继续走，托管条目保存自己的有效剩余延迟。非环境步骤不减少；环境机会消耗有效时间。到期时将条目交回正常队列/回调，并保留 `priority` 与 `subTickOrder`。[S02][S10]

不得只在到期回调 HEAD cancel 后丢掉条目：原版队列此时已先弹出任务。也不得每服务器 tick 将所有条目重新 `scheduleTick(..., 1)`，这会改变顺序、去重和延迟。[S02]

`delay=0` 仍属于计划队列，不自动变成同步调用或永久豁免。它应在原版可处理阶段且环境有执行机会时运行。多个回调共享同一个步骤预算，不是每个回调各领取一个新的环境 tick。

### 8.2 步骤内的出生与重入

复用现有 `bornStep` 的目的：新安排的正延迟任务不应在同一个有效步骤被重复扣减。该标记是时间归属，不是玩家因果身份。[S10]

方块队列、流体队列、方块事件、实体、BE 的先后应按目标版本原版阶段执行。不能统一规定“所有新对象必须等下一整个环境回合”；也不能反复排空新生任务，让 delay 与循环的时间成本消失。

新 TNT 如果在方块阶段点燃，其本步是否进入实体更新，尊重目标版本容器资格。测试要锁定该时序；切勿先强行 tick 一次，再让原版容器第二次执行。

### 8.3 BE 和其他计时风格

内部倒计数可以通过控制正确入口推进；`gameTime % period`、绝对到期时间、太阳/天气条件不能只靠少调用几次保证等待隔离。需要逐机制使用局部环境时间投影、截止时间调整或明确的环境输入策略。[S07][S12]

不要全局伪造 `Level.getGameTime()`，也不要让一次环境步骤内部的所有代码看到不一致的时间。只适配已登记机制依赖的时间输入，范围外维持原版。

随机更新采用规则化环境采样机会，不补偿现实等待时长。只跳过回调仍可能使用已在等待期间推进的全局随机流；严格要求同种子同操作逐结果相同时，还要隔离环境采样随机源。首轮必须区分“有效推进机会一致”与“完全确定性重放已实现”，不能混报。

### 8.4 存档、退出与失败

托管状态保存为有效剩余进度，而非恢复后已过去的绝对世界截止时间。结束遭遇、区块卸载、域合并时复用并验证现有迁移规则，保证一次释放、不重复触发。[S10]

世界步骤发生部分副作用后异常，不能简单重试同一爆炸或搬运。现有中止路径承认未知部分结果并清理执行所有权，应保留这种约束；不要添加“失败后自动补一整个环境 tick”。[S01]

## 9. 维护白名单应很小，且不能替代环境分类

首版可以确认的 P 候选包括客户端箱盖/附魔书/头颅动画、营火粒子、告示牌失效编辑者维护、已知陶罐摆动事件。必须使用精确逻辑侧、类型和入口；不能从一个安全方法推导整个方块类安全。[S09][S11][S12]

不能因为叫“复位”“动画”“检查”，就放开服务端状态变化。红石灯熄灭、按钮弹起、潜影盒开合、容器打开人数变化，都可能有权威副作用。首轮把不确定的权威时间回调继续归 E，即可避免为证明“无害”而设计昂贵的动态世界分析。

## 10. 第一轮实施顺序

### 阶段 A：固定分类与测试合同

先在 `.84` 对照核实 TNT、Button、Diode、BigDripleaf、LilyPad、Hopper 的完整调用路径，补齐基准测试。修改旧文档中 `REACTION`、实体来源继承及“玩家触发必须立即完成”的要求。保留现有框架骨架，不升级版本。

### 阶段 B：粗通道策略与精确 P 例外

继续托管计划 block/fluid；将 BE / blockEvent 策略移到能够识别具体身份的边界；仅放行已审计 P。直接操作与同步邻居响应不再受到错误的环境阶段总门禁约束。活塞/侦测器/中继器不因玩家触发而开洞。

### 阶段 C：TNT、Hopper 和两类“叶片”闭环

TNT 实体增加 E 类别并核对客户端；Hopper 补接触自动转移入口；BigDripleaf 验证已有计划门禁；普通 LilyPad 按明确接触规则适配。此阶段是用户示例必须真正通过的最小闭环。

### 阶段 D：时间与生命周期回归

覆盖出生步骤、保存/重载、全局 freeze、域边界、异常后不重放，检查爆炸伤害、死亡/掉落链。对仍依赖旧整实体冻结而停滞的死亡清理，登记并处理必要生命周期兼容，不能因画面消失就认为服务器已移除。

常规 Mob 主动控制与身体模拟分离仍是后续架构事项。不要为了本轮 TNT 通关而临时解除所有 Mob 的外层冻结；目前 Mob AI 抑制依赖移动许可路径，直接解除会带来未授权自主行为风险。该风险已由前次源码审查指出，不能用本轮方块重构掩盖。

## 12. 给实施者的禁止事项

不得重新引入世界只在环境回合运行的总开关；不得把环境回合改成只收集找不到玩家来源的事件；不得追踪原始玩家来决定中继器/水流能否更新。

不得把持有回合等同于持续计时资格；不得因一次按钮操作就给整个红石网络永久许可；不得为了“完成后续反应”把所有延迟队列一次性排空。

不得将普通荷叶写成具有 BigDripleaf 的倒伏 tick；不得声称漏斗只有 BE ticker；不得把点燃 TNT 写成同步爆炸；不得自动把任何受管控实体都加入先攻表。

不得删除现有延期保存/去重/卸载设施；不得在到期入口直接取消而丢任务；不得从玩家包处理线程异步修改世界；不得因环境执行异常自动重试爆炸或库存转移。

不得在未经审计的普通 Mob 上解除整实体冻结来让 TNT 工作；不得把摄像机/客户端动画修复当成权威世界行为已修复的证据。
